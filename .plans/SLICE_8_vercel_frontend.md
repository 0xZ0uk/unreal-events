# SLICE 8 — Vercel frontend + shared Turso DB

**Goal:** drop the persistent Hono server. Deploy `apps/web` as a static SPA on
Vercel, reading from a Turso (libSQL) database that the local daily runner
writes to. One writer (the 07:00 scrape cron), one reader (the browser).

## Why

The Hono server exists only to serve the DB to the web app and to serve
`/events.ics`. Both can move: the browser can speak libSQL over HTTP directly,
and the ICS file can be generated by the runner that already has the data.

## Architecture

```
07:00 cron (this host)          Vercel (static)
  scraper ──┐                     apps/web  ──read-only token──> Turso
            ├──> Turso  <────────────────────────────────────────┘
  events.ics┘
```

- **Writer:** local runner (scrape + digest + ICS), full-access token.
- **Reader:** browser, `@libsql/client/web` over SQL-over-HTTP, read-only token.
- **No server process anywhere.**

## Pieces

### 1. `packages/db` — browser-safe entry

- Keep `src/index.ts` as the server path (env-driven, unchanged for the runner).
- Add `src/browser.ts` exporting `createBrowserDb(url, authToken)` that builds
  the same drizzle instance on top of `@libsql/client/web`.
- Add `"./browser"` to the package `exports` map.
- `drizzle.config.ts`: support `authToken` from `TURSO_AUTH_TOKEN` so
  `db:push` can target Turso.

### 2. `packages/api` — db from context, not a module singleton

Every router currently imports the `db` singleton from `@events-tracker/db`,
which drags `@events-tracker/env/server` (dotenv, process.env) into any bundle
that touches the router. That is what makes the routers server-only today.

- `createContext` returns `{ db, auth: null, session: null }`.
- Routers take the drizzle handle from `ctx.db` instead of the import.
- Server `createContext` injects the server db (unchanged behaviour there).
- Pure helpers (`grouping.ts`) stay importable from anywhere — no I/O, no env.

Net effect: the same router code runs in the browser, against the same schema,
with zero query duplication.

### 3. `apps/web` — local tRPC link

The route components should not change. Keep the `trpc.*` surface by swapping
`httpBatchLink` for a link that calls `appRouter.createCaller(ctx)` in-process:

```ts
// utils/trpc.ts
const context = { db: createBrowserDb(env.VITE_TURSO_URL, env.VITE_TURSO_AUTH_TOKEN),
                  auth: null, session: null };
// localLink: op => Promise.resolve(caller[op.path](op.input))
```

- `packages/env/src/web.ts`: replace `VITE_SERVER_URL` with
  `VITE_TURSO_URL` (string) + `VITE_TURSO_AUTH_TOKEN` (optional string).
- Remove the now-dead `getServerUrl` Vercel/`SERVER_URL` fallback logic.
- Test data flow: browser → drizzle → libSQL HTTP → Turso.

Fallback if the local link fights the tRPC link plumbing: call the caller
directly from react-query (`queryFn: () => caller.events.byDay()`). Same
queries, same shapes, ~10 call sites touched.

### 4. ICS feed

`/events.ics` was a server route. Move generation into the runner:

- Reuse `buildIcs` from `apps/server/src/digest-core.ts`.
- Runner writes `apps/web/public/events.ics`, commits, pushes to `master`.
- Vercel's git integration redeploys, so the subscription URL is
  `https://<app>.vercel.app/events.ics` — stable, cache-friendly, no server.
- Replace the 4 hardcoded `http://localhost:3301/events.ics` links with a
  relative `/events.ics`.

Alternative if daily commits get noisy: upload to R2/S3 and point at that URL.

### 5. Vercel

- `apps/web/vercel.json`: SPA rewrite (`/(.*)` → `/index.html`), Vite preset.
- Root directory `apps/web`; pnpm workspace install handled by Vercel's
  monorepo detection.
- Env: `VITE_TURSO_URL`, `VITE_TURSO_AUTH_TOKEN`.
- Note: `VITE_*` is inlined at build time. The token is in the bundle by
  design — it is read-only and the data is public events.

### 6. Data migration

- `turso db create unreal-events`
- `db:push` against Turso (drizzle, dialect already `turso`)
- Copy `local.db` rows up (venues, events, event_sources, scrape_runs) rather
  than re-scraping — keeps run history and the 191 existing events.

## Risks / open questions

- **Browser CORS against Turso.** SQL-over-HTTP from a browser is a supported
  Turso pattern, but verify with a real request before building on it. If the
  endpoint refuses the origin, fall back to one Vercel serverless function
  holding the db handle (the context change in §2 makes that a small edit).
- **Read-only token in the bundle.** Accepted: public data, read-only scopes.
- Scrapers keep running locally — Vercel is not asked to do batch work.
